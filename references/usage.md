# 使用方法

`api-doc-to-mcp` 用于把已有 API 文档转成可评审、可测试、可部署的 MCP 集成方案，或审计一个已经存在的 API-to-MCP 封装。它适合在拿到接口文档后，统一完成接口盘点、MCP 能力设计、权限与风险审查、代码实现和验证。

## 触发 Skill

在请求中显式使用 `$api-doc-to-mcp`，或者直接描述“把这份 API 文档封装成 MCP”。推荐显式写出目标，以便 Skill 判断应该生成代码还是只做分析。

最小调用示例：

```text
$api-doc-to-mcp

请根据附件中的 OpenAPI 文档，把订单查询接口封装成 MCP。先完成接口到 Tool 的映射，再生成可运行实现，并说明需要补充的认证配置。
```

也可以通过自然语言隐式触发：

```text
请把这份 Swagger 文档转换成 MCP Server，保留现有权限边界，并给出测试结果。
```

## 支持的输入

可以提供以下任一种或多种材料：

- OpenAPI / Swagger JSON 或 YAML
- Postman Collection
- Markdown、Word、PDF、HTML 等接口说明
- 已有 API 客户端、SDK、MCP Server 或适配器代码
- 接口样例、错误码表、认证说明、租户隔离说明、部署配置和测试命令

结构化文档优先使用原始文件；如果只有截图或粘贴文本，Skill 会把无法核实的字段标记为 `unknown`，不会根据常见习惯补全认证、租户或权限规则。

## 推荐请求模板

提供以下信息可以减少返工：

```text
$api-doc-to-mcp

目标：构建 / 仅分析 / 审计现有封装
接口文档：<文件路径或内容>
目标仓库：<仓库路径；没有则说明只需要方案>
技术栈：<语言、框架、MCP SDK；未知可留空>
部署方式：stdio / Streamable HTTP / 其他
认证方式：<OAuth、API Key、网关会话等；未知请写“未知”>
租户与权限：<已知边界；未知请写“未知”>
范围：<需要纳入的业务能力>
排除项：<不允许暴露的接口或数据>
验证方式：<测试命令、沙箱地址或只能使用 Mock 的限制>
```

如果目标仓库已经存在，应同时给出仓库路径和期望的启动命令。Skill 会优先沿用仓库的语言、框架、目录结构、MCP SDK 和测试方式。

## 三种常见用法

### 1. 构建 MCP Server

适用于希望得到代码、配置说明和测试结果的场景。

```text
$api-doc-to-mcp

根据 `docs/order-api.yaml` 构建一个订单 MCP Server。
只纳入订单查询、订单详情和物流状态查询；不要暴露登录、健康检查、调试和删除接口。
项目使用 TypeScript，目标传输为 Streamable HTTP。先输出映射和风险清单，确认后再实现。
```

这类请求通常会产出：

1. 接口库存和 API 到 Tool / Resource / Prompt 的映射
2. 排除项、假设、未知项和风险分级
3. 按现有项目技术栈生成或修改的 MCP 实现
4. 配置与启动说明，敏感值只以环境变量或配置引用表示
5. 类型检查、构建和聚焦测试结果
6. `ready`、`conditional` 或 `blocked` 状态及其依据

涉及写入、审批、删除、支付、外发或特权下载时，先要求确认映射、权限、幂等和确认语义；信息不足时会保持禁用或 `pending-review`。

### 2. 只做分析或方案设计

在不修改代码的情况下，要求输出标准化映射和实施计划：

```text
$api-doc-to-mcp

只分析，不生成代码。请读取 `docs/catalog-openapi.json`，输出：
- 接口库存
- Tool / Resource / Prompt 映射
- 认证、租户隔离和敏感数据缺口
- 高风险接口清单
- 分阶段实施计划和验收标准
```

此模式适合文档尚未完整、需要先评审边界，或暂时没有目标仓库的情况。只读、低风险且证据完整的分析可以继续；未知的安全边界会明确保留为未知。

### 3. 审计现有 API-to-MCP 封装

提供现有 MCP 代码、对应 API 文档和测试命令：

```text
$api-doc-to-mcp

请审计 `src/mcp-server` 是否正确封装 `docs/api.yaml`。
重点检查：接口覆盖、权限是否由服务端派生、租户隔离、敏感字段脱敏、分页、超时、重试和高风险操作确认。
不要重写代码，按风险优先级给出问题、证据和修复建议。
```

审计结果应区分已证实的问题、文档缺口和无法验证的运行时行为，不会把“测试未覆盖”当成“实现正确”。

## 不完整文档的用法

文档缺少认证、租户、权限、错误码或字段定义时，直接说明限制即可：

```text
$api-doc-to-mcp

这份文档没有写认证和租户规则。请先做 review-only 分析，保留所有未知项，输出需要向后端确认的问题；不要生成可执行的写操作。
```

Skill 会把缺口记录为假设或待确认项，必要时将结果设为 `conditional` 或 `blocked`。不会猜测默认租户、角色、审批人、授权请求头或删除语义。

## 高风险接口的用法

对删除、支付、审批、发送外部消息、批量修改、权限变更和特权文件下载，应明确要求风险审查：

```text
$api-doc-to-mcp

请评估支付和退款接口是否适合暴露为 MCP Tool。
只输出风险评估、所需权限、确认步骤、幂等要求、审计字段和阻塞条件，不执行真实调用。
```

缺少服务端授权、用户确认、幂等键、审计要求或租户边界时，结果应停在 `pending-review` / `blocked`，不能通过“接口文档看起来完整”推断为可上线。

## 如何理解输出状态

- `ready`：映射、权限与隔离、敏感数据、运行验证和发布检查均有证据支持，剩余风险已记录。
- `conditional`：可以用于开发、沙箱或受限场景，但仍有明确的模拟测试、下游不可用或发布门禁缺口。
- `blocked`：存在未解决的权限、租户隔离、高风险副作用、关键构建失败或无法验证的安全边界，不应作为可运行生产集成交付。

看到 `conditional` 或 `blocked` 时，应优先补齐输出中列出的证据和确认项，再重新运行 Skill；不要只要求“直接生成代码”来绕过检查点。

## 使用限制

- 不会从接口路径或常见框架约定推断真实权限、认证或租户规则。
- 不会把所有 API 端点机械地暴露成 MCP Tool。
- 不会把密钥、令牌、真实生产地址写入源码、Schema 或示例配置。
- 不会自动执行删除、支付、审批、外发或其他不可逆操作。
- 没有真实下游时可以使用契约 Fixture 或 Mock，但会明确标注模拟覆盖范围。
- 只有用户要求构建或修改时才生成代码；“只分析”请求只返回映射、审查和计划。
